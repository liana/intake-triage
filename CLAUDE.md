# intake-triage — working rules

`SPEC.md` is the source of truth for *what* we're building and `DECISIONS.md` for *why*;
this file is only *how*. Update `DECISIONS.md` when a decision changes.

## How to work here

- **Simplest thing that works.** No speculative abstraction, no error handling for cases
  that can't happen, no configurability nobody asked for. Three similar lines beat a
  premature abstraction.
- **Scan before writing.** Reuse or extend the closest existing pattern rather than
  adding a parallel one.
- **New code looks like existing code.** Consistency beats local optimization.
- **Layers don't skip.** Components never call Prisma or the Anthropic SDK directly;
  lib modules never return JSX. One concern per module.
- **Explicit over implicit.** A reader traces behavior by reading the code, not by
  knowing framework internals.
- **Abstract only at boundaries.** A function called from one place needn't be extracted.
- **Validate at the boundary.** Server-side validation is authoritative; never trust a
  client-side check.
- **Business rules live as data** — named constants blocks, not scattered conditionals.
- **Before adding a dependency:** is there a lighter option, or something already
  installed that covers it? Every package is maintenance debt.
- **UI & frontend design.** Use the installed `frontend-design` skill when creating a new
  view or establishing the design system — settle typography, palette, and layout before
  building the screen. If the skill isn't available, say so rather than silently styling
  from scratch.
- **Interactive workflow.** You own the checkpoints. Never run `git commit` or `git push`
  unless asked. Anything destructive or hard to reverse, and any large refactor, gets a
  plan for review before it runs — when unsure whether something qualifies, ask. Routine
  new code inside an agreed gate needs no pre-approval.
- **Stay in scope.** Fix what was asked; don't refactor the surrounding file, and don't
  improvise a product decision that belongs in the spec. Work the build gates in order,
  setup first. Flag a step before skipping it, and if we run long, cut scope explicitly
  in the agreed abandon order rather than silently.
- **Never paraphrase figures.** Budget numbers, dates, and timelines in generated output
  are copied verbatim, never rounded or reworded.
- **Run the check, don't describe it.** The build gates define done. UI claims need the
  browser; headless claims need a script or curl. `npm run build` typechecks, so
  `tsc --noEmit` is the fast inner loop, not a second gate. There is no linter and no
  test runner here — never report a lint or test pass.

## Stack traps

- **Next 16 route params are Promises.** `await` them. Type them with the global helpers —
  `PageProps<'/intakes/[id]'>` for pages, `RouteContext<'/api/intakes/[id]'>` for route
  handlers — which need no import and are generated by `next dev`, `next build`, or
  `next typegen`. Writing `params.id` synchronously, the pre-16 form, fails here.
- **Prisma Client generates to `src/generated/prisma`**, gitignored with no `postinstall`.
  Import from `@/generated/prisma` — `@prisma/client` is installed, so the wrong import
  typechecks and fails at runtime. Run `npx prisma generate` after a clone or schema edit.
- **SQLite has no enums and no scalar lists.** Vocabulary columns are `String`; multi-value
  fields are JSON strings parsed at the boundary with Zod. "Fixing" them to `String[]` or a
  Prisma enum fails the migration.
- **Tailwind v4 has no `tailwind.config.js`.** The theme lives in `globals.css` under
  `@theme`. Don't create the config file.
- **`ANTHROPIC_API_KEY` is server-only.** Never `NEXT_PUBLIC_`, never imported into a
  Client Component. No secret is ever committed; `.env*` is gitignored.
